# 学报稿件审稿业务规范与现状差距分析

> 文档版本：v1.0 | 日期：2026-06-13 | 作者：学报编辑部技术组

## 一、文档目的

本文档面向学报编辑部技术负责人与开发团队，梳理当前稿件管理系统（`gaojiaoguanli`）在盲审流程方面的业务规范，对照代码实现与数据库设计，明确"应有"与"已有"之间的差距，为后续迭代提供依据。

## 三、状态机设计

### 3.1 理想审稿流程

```
作者投稿
  |
  v
+--------+    管理员分配专家    +----------+    专家审稿    +--------+
| 待审(1)|------------------->| 审稿中(2)|-------------->| 修回(3)|
+--------+                    +----------+               +--------+
  ^                                                       |       |
  |                  作者修回重提                           |       |
  +-------------------------------------------------------+       |
                                                                  |
                                                        管理员终裁 |
                                                        +---------+---------+
                                                        |                   |
                                                        v                   v
                                                   +--------+          +--------+
                                                   | 录用(4)|          | 退稿(5)|
                                                   | [终态] |          | [终态] |
                                                   +--------+          +--------+
```

### 3.2 状态转换规则（代码已实现部分）

| 当前状态 | 触发动作 | 目标状态 | 操作角色 | 代码位置 |
|----------|----------|----------|----------|----------|
| (无) → 待审(1) | `save` 投稿 | 待审(1) | 作者 | `GaojianController.save()` |
| 待审(1) → 审稿中(2) | `assign` / `autoAssign` | 审稿中(2) | 管理员 | `GaojianController.assign()` / `autoAssign()` |
| 审稿中(2) → 修回(3) | `review` 结论=修回 | 修回(3) | 专家 | `GaojianController.review()` |
| 审稿中(2) → 录用(4) | `review` 结论=录用 | 录用(4) | 专家 | `GaojianController.review()` |
| 审稿中(2) → 退稿(5) | `review` 结论=退稿 | 退稿(5) | 专家 | `GaojianController.review()` |
| 修回(3) → 待审(1) | `revision` 修回重提 | 待审(1) | 作者 | `GaojianController.revision()` |
| 修回(3) → 录用(4) | `finalDecision` 录用 | 录用(4) | 管理员 | `GaojianController.finalDecision()` |
| 修回(3) → 退稿(5) | `finalDecision` 退稿 | 退稿(5) | 管理员 | `GaojianController.finalDecision()` |

### 3.3 状态机已实现的保护机制

- **终态不可变**：`update` 接口强制将 `gaojianStatusTypes`、`gaojianYesnoTypes`、`gaojianShenheContent`、`zhuanjiaId` 置 null，阻止通过通用更新接口篡改状态。
- **角色互斥**：专家不能走 `update`，必须走 `/review`；作者投稿后不能自行改状态。
- **审稿意见链**：每次审稿/修回/终裁操作均向 `gaojianYesnoText` JSON 数组追加记录，含轮次、角色、结论、时间戳，形成完整审计轨迹。
- **文件版本历史**：作者修回时，旧文件路径存入 `gaojianFileHistory` JSON 数组，保留历史版本。

### 3.4 状态机缺失与差距

| 缺失项 | 说明 | 风险等级 |
|--------|------|:--------:|
| **专家可直接给出录用/退稿结论** | `review()` 接口允许专家选择结论 3(修回)/4(录用)/5(退稿)。按学报规范，专家应仅能建议"修回/建议录用/建议退稿"，最终录用/退稿应由主编或管理员终裁。当前代码中专家可直接将稿件推入终态(4或5)，绕过管理员终裁。 | **高** |
| **缺少"审稿中→退修→再审"多轮循环** | 专家只能一次性给出结论，没有"副主编复审"或"多专家并行审稿"的设计。 | 中 |
| **缺少超时催审机制** | 无定时任务检测审稿超时，无提醒通知。 | 中 |
| **缺少撤稿/申诉状态** | 已录用稿件无法走撤稿流程，作者无法对退稿发起申诉。 | 低 |
| **状态回退无约束** | 修回重提后回到"待审(1)"而非直接进入"审稿中(2)"，需管理员再次分配（可能是不同专家），业务合理性需确认。 | 低 |

### 4.2 对接差距明细

#### 4.2.1 ZhuanjiaDao.xml 列缺失

`ZhuanjiaDao.xml` 的 `Base_Column_List` 未包含 `zhuanjia_gaojian_types`，导致：
- 专家列表页无法展示"擅长学科"
- 前端无法按学科筛选专家
- 虽然 `autoAssignExpert()` 通过 `zhuanjiaService.selectList()` 查询完整实体（绕过 XML 列列表），功能本身不受影响，但管理界面信息不完整。

#### 4.2.2 GaojianVO / GaojianModel 未包含盲审字段

`GaojianVO.java` 和 `GaojianModel.java` 均不包含以下字段：
- `gaojianStatusTypes`
- `gaojianFileHistory`
- `gaojianYesnoText`

影响：如果有移动端或外部 API 通过 VO/Model 进行序列化，将无法获取稿件状态、文件历史和审稿意见链。

#### 4.2.3 Flyway 迁移脚本

`V2__blind_review.sql` 已编写为幂等版本（使用 `safe_add_column` 存储过程 + `NOT EXISTS` 防重），可安全重复执行。Flyway 配置正确（`baselineOnMigrate=true`，依赖关系确保先于 MyBatis 初始化）。

## 五、page 接口越权风险（已知问题）

### 5.1 问题描述

`GaojianController.page()` 接口中，**专家角色的数据过滤逻辑被注释**（或已删除），当前实现为：

```java
// 角色过滤
if ("作者".equals(role)) {
    params.put("zuozheId", userId);
} else if ("专家".equals(role)) {
    params.put("zhuanjiaId", userId);
}
// 管理员不过滤，可看全部
```

虽然代码逻辑上专家只能看到分配给自己的稿件（通过 `zhuanjiaId` 过滤），但存在以下风险：

1. **前端传参覆盖**：如果 `params` 中的 `zhuanjiaId` 可被前端请求参数覆盖（取决于参数绑定顺序和优先级），专家可能构造请求查看他人稿件。
2. **无二次校验**：查询结果返回后，未在后端逐条校验当前专家是否为稿件的指定审稿人。
3. **敏感信息泄露**：返回的 `GaojianView` 包含作者姓名（`zuozheName`）、身份证号（`zuozheIdNumber`）等信息，违反盲审原则。

### 5.2 建议修复方向

- 在 Service 层强制注入当前用户的过滤条件，不接受前端传参覆盖。
- 专家视图应脱敏处理作者信息（隐藏姓名、身份证号）。
- 添加单元测试验证专家无法通过修改请求参数查看非本人稿件。

## 七、其他已知问题

### 7.1 orderBy SQL 注入风险

`GaojianDao.xml` 的 `selectListView` 查询中使用了 `${}` 直接拼接排序字段：

```xml
order by a.${params.orderBy} desc
```

`${}` 是 MyBatis 的字符串替换（非预编译参数），攻击者可通过 `orderBy` 参数注入 SQL。应改为白名单校验或使用 `<choose>` 标签限定可排序字段。

### 7.2 角色硬编码

`"管理员"`、`"作者"`、`"专家"` 三个角色字符串散落在所有 Controller 中，无枚举类或常量类统一管理。一旦角色名称变更，需全局搜索替换，维护风险高。

### 7.3 事务边界

`GaojianServiceImpl` 类级别标注 `@Transactional`，但 Controller 中的多步操作（如 `review()` 先读取、修改 Entity、再写回）未在 Controller 层声明事务，依赖 Service 层默认事务。若后续引入跨 Service 调用，可能出现事务不一致。

| P0 | orderBy SQL 注入修复 | 小 |

| P1 | GaojianVO/Model 补充盲审字段 | 小 |
| P1 | ZhuanjiaDao.xml 补充 zhuanjia_gaojian_types 列 | 小 |
| P2 | 角色枚举化，统一常量管理 | 中 |
