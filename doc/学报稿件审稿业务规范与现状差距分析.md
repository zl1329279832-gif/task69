# 学报稿件审稿业务规范与现状差距分析

> 文档基于 `gaojiaoguanli` 项目源码（`GaojianEntity`、`GaojianController`、`GaojianServiceImpl`、`GaojianDao.xml`、`blind_review.sql`）编写。仅做现状梳理与差距说明，不涉及代码修改。

---

## 一、GaojianEntity 核心字段说明

| 字段 | 列名 | 类型 | 业务含义 |
|------|------|------|----------|
| `gaojianYesnoTypes` | `gaojian_yesno_types` | INT | **审稿结果码**。投稿时初始化为 `1`；专家审稿（`/review`）或管理员终裁（`/finalDecision`）后被写入结论码（3=修回、4=录用、5=退稿）。语义上与 `gaojianStatusTypes` 高度重叠，详见「已知问题-P2」。 |
| `gaojianYesnoText` | `gaojian_yesno_text` | TEXT | **审稿意见链**（JSON 数组）。每一轮审稿/修回/终裁追加一条 JSON 对象，记录 `round`、`role`、`content`、`conclusion`、`conclusionCode`、`time`。投稿时初始化为 `"[]"`。 |
| `gaojianFile` | `gaojian_file` | VARCHAR | **当前版本稿件文件路径**（仅文件名，如 `1718234567890.docx`）。作者修回时被替换为新文件，旧文件路径归档到 `gaojianFileHistory`。 |
| `gaojianStatusTypes` | `gaojian_status_types` | INT | **稿件流程状态**。由 `blind_review.sql` 新增，取值：1=待审、2=审稿中、3=修回、4=录用、5=退稿。所有流程端点以此字段做前置状态校验。 |
| `gaojianFileHistory` | `gaojian_file_history` | TEXT | **历史文件版本**（JSON 数组）。每次修回重提时，将当前 `gaojianFile` 及时间戳追加到数组中。由 `blind_review.sql` 新增。 |
| `gaojianShenheContent` | `gaojian_shenhe_content` | VARCHAR | **最近一次审核回复**（纯文本）。每次 `/review` 时被覆盖写入，不保留历史——历史保留在 `gaojianYesnoText` 意见链中。 |

### 字段关系图

```
gaojianFile ──(修回时归档)──> gaojianFileHistory[]
                                   │
gaojianShenheContent               │  共同构成完整审稿历程
     │                             │
     └── 最新一条 ─── 同步写入 ──> gaojianYesnoText[]
```

## 二、三角色权限矩阵

以下矩阵基于 `GaojianController` 各端点的 `role` 校验逻辑整理。

| 端点 | 作者 | 专家 | 管理员 | 前置状态要求 | 状态变迁 |
|------|:----:|:----:|:------:|:-------------|:---------|
| `POST /gaojian/save` | **允许** | 拒绝 | 拒绝 | 无 | → 待审(1) |
| `POST /gaojian/update` | 仅自己稿件，只改基本字段 | **拒绝**（提示走 /review） | 允许，但不能改状态 | 无 | 不变 |
| `POST /gaojian/delete` | 拒绝 | 拒绝 | **允许** | 无 | 物理删除 |
| `POST /gaojian/assign` | 拒绝 | 拒绝 | **允许** | 待审(1) | → 审稿中(2) |
| `POST /gaojian/autoAssign` | 拒绝 | 拒绝 | **允许** | 待审(1) | → 审稿中(2) |
| `POST /gaojian/review` | 拒绝 | **仅被分配专家** | 拒绝 | 审稿中(2) | → 修回(3)/录用(4)/退稿(5) |
| `POST /gaojian/revision` | **仅稿件作者** | 拒绝 | 拒绝 | 修回(3) | → 待审(1) |
| `POST /gaojian/finalDecision` | 拒绝 | 拒绝 | **允许** | 修回(3) | → 录用(4)/退稿(5) |
| `GET /gaojian/page` | 仅自己稿件 | 仅分配给自己的稿件 | 全部 | 无 | 不变 |
| `GET /gaojian/info/{id}` | 无过滤 | 无过滤 | 无过滤 | 无 | 不变 |

### 权限控制方式

- **角色判断**：通过 `request.getSession().getAttribute("role")` 获取字符串角色名（`"作者"` / `"专家"` / `"管理员"`），硬编码比较。
- **数据隔离**：`page` 方法在 Controller 层向查询参数注入 `zuozheId` 或 `zhuanjiaId`，由 MyBatis mapper 的 `<if>` 条件拼接 SQL WHERE。`info` 端点无数据隔离。
- **状态校验**：各流程端点在方法体内手动校验 `gaojianStatusTypes`，无统一拦截器。

## 三、现有状态机与缺失分析

### 3.1 当前实现的状态机

```
                       ┌──────────────────────────────────────────┐
                       │              作者修回重提                 │
                       │           POST /revision                 │
                       ▼                                          │
 ┌──────────┐   assign/autoAssign   ┌──────────┐   /review   ┌───┴──────┐
 │  待审(1)  │ ─────────────────── > │ 审稿中(2) │ ────────── > │  修回(3)  │
 └──────────┘    管理员分配专家      └──────────┘  专家提交    └──────────┘
   ▲ save                                │ /review                 │ /finalDecision
   │ 作者投稿                            │                         │ 管理员终裁
                                         ▼                         ▼
                                    ┌──────────┐           ┌──────────┐
                                    │  录用(4)  │           │  退稿(5)  │
                                    └──────────┘           └──────────┘
                                         ▲                         ▲
                                         │      /finalDecision     │
                                         └────── 管理员终裁 ───────┘
```

状态常量定义于 `GaojianController` 静态字段（第 52-60 行）：

```java
public static final int STATUS_DAI_SHEN = 1;      // 待审
public static final int STATUS_SHEN_GAO_ZHONG = 2; // 审稿中
public static final int STATUS_XIU_HUI = 3;        // 修回
public static final int STATUS_LU_YONG = 4;        // 录用
public static final int STATUS_TUI_GAO = 5;        // 退稿
```

### 3.2 缺失项

| 缺失项 | 影响 | 建议 |
|--------|------|------|
| **无状态枚举 / 状态机类** | 状态码散落在 Controller 常量中，难以集中维护；新增状态需修改多处 | 抽取 `GaojianStatus` 枚举，包含合法转换映射 |
| **无统一状态转换校验拦截器** | 每个端点自行校验前置状态，逻辑重复且易遗漏 | 实现 `StateMachineInterceptor` 或 AOP |
| **无"撤稿"状态** | 作者投稿后无法主动撤回 | 新增状态 6=撤稿，仅待审(1)状态允许 |
| **无审稿超时 / 催审机制** | 稿件可无限停留在"审稿中"状态 | 新增 `review_deadline` 字段 + 定时任务 |
| **无审稿轮次上限** | 修回→待审可无限循环 | 在意见链长度上做限制或加轮次字段 |
| **无操作审计日志表** | 所有状态变更仅靠 `gaojianYesnoText` JSON 记录，无独立审计表 | 新增 `gaojian_audit_log` 表 |
| **终裁仅限修回(3)状态** | 管理员无法直接从审稿中(2)终裁（如专家弃审场景） | 扩展 `finalDecision` 允许从状态 2 终裁 |

## 四、blind_review.sql 库表设计与代码对接分析

### 4.1 SQL 脚本内容

`blind_review.sql`（及其幂等版本 `V2__blind_review.sql`）执行以下变更：

1. **gaojian 表新增三列**：`gaojian_status_types`、`gaojian_file_history`、`gaojian_yesno_text`
2. **zhuanjia 表新增一列**：`zhuanjia_gaojian_types`（专家擅长学科，逗号分隔）
3. **新建 liyi_chongtu 表**：利益冲突关系表（`zuozhe_id` + `zhuanjia_id`，唯一索引）
4. **字典数据插入**：`gaojian_status_types` 的 5 种状态名称

### 4.2 代码对接现状

| SQL 变更 | Entity 是否有对应字段 | Mapper 是否查询 | Controller 是否使用 | 对接结论 |
|----------|:--------------------:|:---------------:|:-------------------:|:--------:|
| `gaojian_status_types` | `gaojianStatusTypes` | `Base_Column_List` 中包含 | save/assign/review/revision/finalDecision 均使用 | **已对接** |
| `gaojian_file_history` | `gaojianFileHistory` | `Base_Column_List` 中包含 | revision 中归档历史文件 | **已对接** |
| `gaojian_yesno_text` | `gaojianYesnoText` | `Base_Column_List` 中包含 | review/revision/finalDecision 追加意见链 | **已对接** |
| `zhuanjia_gaojian_types` | `ZhuanjiaEntity` 中需确认 | 在 `autoAssignExpert` 方法中通过 `expert.getZhuanjiaGaojianTypes()` 读取 | autoAssign 使用 | **已对接** |
| `liyi_chongtu` 表 | `LiyiChongtuEntity` 存在 | `LiyiChongtuService.findConflictExpertIds()` | autoAssign 排除利益冲突专家 | **已对接** |
| 字典表数据 | — | `dictionaryService.dictionaryConvert()` 在 page/info 中使用 | 状态码转中文显示名 | **已对接** |

### 4.3 未对接 / 存在差距的部分

| 问题 | 详情 |
|------|------|
| **"盲审"名不副实** | SQL 脚本取名 `blind_review`，但实际查询（`GaojianDao.xml` 第 27-34 行）通过 `LEFT JOIN zuozhe` 将作者姓名（`zuozhe_name`）、身份证号（`zuozhe_id_number`）、地址（`zuozhe_address`）等信息暴露给所有角色，包括专家。真正的盲审需在专家视图中屏蔽作者信息。 |
| **`gaojianYesnoText` 字段复用** | 该列名在 SQL 中新建，但 `gaojian_yesno_text` 原本在某些生成器版本中可能已存在（作为"审核意见"文本字段）。现在被复用为 JSON 数组存储意见链，旧数据迁移需注意格式兼容。 |
| **V2 迁移依赖存储过程** | `V2__blind_review.sql` 使用 `safe_add_column` 存储过程实现幂等，但 Flyway 等迁移框架默认不支持 `DELIMITER` 语法，实际执行方式需确认。 |

## 五、理想审稿流与现状对比

### 5.1 理想盲审流程

```
作者投稿 ──> [编辑部初审] ──> 待审
                                │
                    编辑部分配专家（系统隐去作者信息）
                                │
                                ▼
                            审稿中 ──> 专家提交意见
                                │          │
                    ┌───────────┼──────────┐
                    ▼           ▼          ▼
                  修回        录用       退稿
                    │                      │
             作者修回重提            通知作者
                    │
                    ▼
              [二审/终审]
                    │
              ┌─────┴─────┐
              ▼           ▼
            录用         退稿
```

### 5.2 对比表

| 维度 | 理想盲审流程 | 当前实现 | 差距 |
|------|-------------|---------|------|
| **作者信息屏蔽** | 专家看不到作者姓名、单位等 | `GaojianDao.xml` JOIN zuozhe 表，专家可见作者全部信息 | **未实现盲审核心要求** |
| **专家信息屏蔽** | 作者看不到审稿专家身份 | `GaojianDao.xml` JOIN zhuanjia 表，作者可见专家姓名和身份证号 | **未实现双盲** |
| **编辑部初审** | 投稿后先经编辑部形式审查 | 投稿直接进入"待审"，无初审环节 | 缺少初审状态 |
| **状态机完整性** | 含撤稿、超时、多轮审 | 5 种状态，无撤稿/超时/轮次限制 | 部分缺失 |
| **利益冲突回避** | 自动匹配时排除冲突专家 | `autoAssignExpert` 已实现冲突排除 | **已实现** |
| **学科匹配分配** | 按稿件学科匹配专家方向 | `autoAssignExpert` 按 `gaojianTypes` 匹配 `zhuanjiaGaojianTypes` | **已实现** |
| **负载均衡** | 均匀分配审稿量 | `autoAssignExpert` 选择当前在审稿件最少的专家 | **已实现** |
| **意见链追溯** | 完整记录每轮审稿/修回过程 | `gaojianYesnoText` JSON 数组逐轮追加 | **已实现** |
| **文件版本管理** | 保留每次修回的历史版本 | `gaojianFileHistory` JSON 数组记录 | **已实现** |
| **通知机制** | 状态变更时邮件/站内信通知 | 无任何通知机制 | 完全缺失 |
| **多专家会审** | 重要稿件可分配多位专家 | `zhuanjiaId` 为单值字段，仅支持一对一 | 不支持 |

## 六、已知问题

### P0：专家 page 接口越权风险

**位置**：`GaojianController.java` 第 91-92 行

```java
else if("专家".equals(role))
    params.put("zhuanjiaId",request.getSession().getAttribute("userId"));
```

当前该过滤逻辑**生效中**，专家仅能看到分配给自己的稿件。但此处存在以下风险：

1. **注释即越权**：这两行代码是专家数据隔离的**唯一屏障**。若被注释掉或在后续重构中遗漏，专家将看到全部稿件（含未分配、分配给其他专家的稿件），构成水平越权漏洞。
2. **info 接口无隔离**：`/gaojian/info/{id}` 端点（第 108-136 行）不做任何角色过滤，专家只要知道稿件 ID 即可查看任意稿件详情（含作者信息），绕过 `page` 的数据隔离。
3. **缺乏防护纵深**：数据隔离仅在 Controller 层用参数注入实现，Mapper/Service 层无二次校验。建议在 Service 层或 MyBatis 拦截器中增加强制过滤。

### P1：盲审信息泄露

**位置**：`GaojianDao.xml` 第 27-34 行

```sql
,zhuanjia.zhuanjia_name as zhuanjiaName
,zhuanjia.zhuanjia_id_number as zhuanjiaIdNumber
,zuozhe.zuozhe_name as zuozheName
,zuozhe.zuozhe_id_number as zuozheIdNumber
,zuozhe.zuozhe_address as zuozheAddress
```

专家查询稿件列表时，SQL 直接 JOIN 了作者表并返回作者姓名、身份证号、地址。作者查询时也能看到专家姓名和身份证号。**这与盲审制度的基本要求矛盾**。

### P2：gaojianYesnoTypes 与 gaojianStatusTypes 语义重叠

**位置**：`GaojianController.java` 第 343-344 行

```java
gaojian.setGaojianYesnoTypes(reviewConclusion);
gaojian.setGaojianStatusTypes(reviewConclusion);
```

两个字段在 `/review` 和 `/finalDecision` 中被写入相同的值。`gaojianYesnoTypes` 本意是"审稿结果"，`gaojianStatusTypes` 是"流程状态"，但实际总是同步赋值。这导致：
- 语义混乱，维护者无法判断应以哪个字段为准
- 修回重提后 `gaojianStatusTypes` 回到 1（待审），但 `gaojianYesnoTypes` 未重置，仍保留上一轮的结论码

### P3：通用接口绕过业务逻辑

**位置**：`CommonController.java`

以下端点接受任意表名和列名，**无角色校验**，可绕过 `GaojianController` 的全部权限与状态校验：

- `POST /sh/{tableName}` — 可直接修改 gaojian 表的审核状态
- `POST /update/{tableName}/{id}/{column}/{value}` — 可直接改写 `gaojian_status_types`、`zhuanjia_id` 等字段
- `POST /plus/{tableName}/{id}/{column}/{number}` / `POST /reduce/...` — 可对整型字段加减

任何已登录用户（含作者和专家）均可通过这些通用接口直接修改稿件状态和审稿结果，使 `GaojianController` 中的角色校验形同虚设。

### P4：SQL 注入风险

**位置**：`GaojianDao.xml` 第 100 行

```xml
order by a.${params.orderBy} desc
```

使用 `${}` 字符串拼接而非 `#{}` 参数化绑定，`orderBy` 参数来自前端请求。攻击者可构造恶意排序表达式注入任意 SQL。虽然 Controller 中硬编码了 `params.put("orderBy","id")`（第 93 行），但 `@RequestParam Map` 中如果前端也传入 `orderBy`，由于 `put` 在后执行会覆盖，当前逻辑恰好安全；但若顺序调整则风险暴露。

## 七、改进建议优先级

| 优先级 | 改进项 | 工作量预估 |
|:------:|--------|-----------|
| **紧急** | 封堵 CommonController 通用接口对 gaojian 表的越权访问 | 小 |
| **紧急** | info 接口增加角色数据隔离 | 小 |
| **高** | 实现盲审信息屏蔽（按角色返回不同视图） | 中 |
| **高** | 将 Mapper orderBy 改为 `#{}` 或白名单校验 | 小 |
| **中** | 抽取状态机枚举，统一状态转换校验 | 中 |
| **中** | 清理 gaojianYesnoTypes 与 gaojianStatusTypes 的双写逻辑 | 小 |
| **低** | 增加通知机制、审稿超时、撤稿状态 | 大 |
